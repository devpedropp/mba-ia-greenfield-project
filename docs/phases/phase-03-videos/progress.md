### SI-03.8 — Cliente de upload Uppy headless (Verification)
- **Status:** completed
- **Tests:** 6 passing (5 unit, 1 integration)
- **Observations:**
  - **Significant architecture gap found and resolved by judgment call (user-confirmed at each step):** AC #2 requires the simulated multipart flow to end by calling `POST /videos/:id/complete` with the collected parts, but neither SI-03.7 nor SI-03.8 had a Technical action to build the code that actually makes that call — both SIs only listed test-writing actions. Tracing `@uppy/aws-s3@6.3.1`'s real internals revealed this isn't a small oversight: the library's default multipart flow completes the upload **itself**, directly against S3/MinIO, via a presigned URL obtained through `signRequest`'s `CompleteMultipartUploadRequest` branch — which directly conflicts with this backend's design (SI-03.4), where the **backend** performs the real `CompleteMultipartUpload` via `POST /videos/:id/complete`. Letting both happen would double-complete the same multipart upload and fail against real S3/MinIO (`NoSuchUpload` on the second attempt).
  - **Resolution (user-approved):** added `UnsupportedMultipartOperationError` to `sign-upload-request.ts` — `signUploadRequest` now explicitly rejects every multipart operation except "sign one part" (`create`, `list`, `complete`, `abort`), instead of silently mis-signing them. Added `lib/upload/complete-upload.ts` (`wireUploadCompletion`), wired into `create-uppy.ts`: it collects parts from the real `s3-multipart:part-uploaded` event, and — specifically when `upload-error` fires with the `"complete"`-flavored `UnsupportedMultipartOperationError` (i.e. every real part already succeeded; only Uppy's own completion attempt was deliberately blocked) — calls this project's own `POST /videos/:id/complete` with the collected parts. This is new production code beyond SI-03.8's literal two Technical actions, added because AC #2 is otherwise unsatisfiable; flagging for the user in case TD-07 should be amended at the source to document this division of responsibility.
  - **Second, separate gap found while tracing the above (not resolved — explicitly deferred):** because this backend always creates the multipart upload *before* Uppy ever sees the file (`POST /videos` runs first), the only way to hand Uppy the existing `uploadId`/`key` is via its "resume" mechanism (`file.s3Multipart`). Uppy treats *any* file with that pre-set state as a resume, which means it unconditionally calls `listParts` first — and `listParts` needs a real **presigned S3 ListParts URL**, which nothing in this project generates (`StorageService` only has presigned PUT-part and GET; no presigned ListParts was built in SI-03.2/03.4). This means a fully real end-to-end Uppy upload against this backend is currently blocked on a backend capability that doesn't exist in any SI of this phase. `signUploadRequest` rejects `list` the same way it rejects `complete` (both via `UnsupportedMultipartOperationError`), so the gap fails loudly rather than silently. Not fixed here — would require a new `StorageService` method plus a new backend contract, which is out of scope for a "write tests" SI; surfacing this for the user to decide whether it needs a new TD before the real upload-screen phase.
  - **Integration test scope, consequently narrowed (user-approved):** `create-uppy.integration.test.ts` exercises the **real** `signUploadRequest` + `wireUploadCompletion` wiring attached to a **real** `Uppy` instance (imported from `create-uppy.ts`, not mocked), but drives it by emitting the same events `@uppy/aws-s3`'s internal engine would emit (`s3-multipart:part-uploaded`, then `upload-error` with the completion sentinel) rather than running that internal engine itself — which the ListParts gap above makes impossible to do honestly today. This proves our own glue code is correct; it does not prove `@uppy/aws-s3`'s internals integrate end-to-end with this backend (blocked by the same gap).
  - `signUploadRequest`'s unit test and the new integration test both needed `// @vitest-environment jsdom`, even though neither renders JSX — `fetch()` with a relative URL (`/api/videos/...`) requires a `document`/`location` base to resolve against; Node's native `fetch` (the Vitest default "node" environment) has no such base and throws `Invalid URL`. Confirmed empirically before relying on it.
  - Extracted `videoIdFromKey` (storage-key → videoId parsing) out of `sign-upload-request.ts` into a new shared `video-id-from-key.ts`, since `complete-upload.ts` needed the identical logic — avoids duplicating it per the project's code-quality conventions.
